# Hoczi Constitution

Hoczi is a teaching & learning platform (HSK Chinese, English, math, science, books, quizzes,
classes, AI-assisted learning). This repository is a monorepo with two applications:
`hoczi-api/` (backend) and `hoczi-web/` (frontend).

## Core Principles

### I. Monorepo Boundaries

- `hoczi-api/` is the only component that owns business rules, the PostgreSQL schema,
  third-party AI/cloud credentials (OpenAI, Anthropic, ElevenLabs, AWS) and background workers.
- `hoczi-web/` MUST reach business data through the API via `hoczi-web/data/services/*` and the
  shared HTTP client in `hoczi-web/data/http`. New direct DB access from the web app is
  forbidden; the existing `hoczi-web/lib/data-source.ts` is legacy and MUST NOT be extended.
- A feature that spans both apps MUST define its API contract (route, request DTO, response
  shape) in the plan before either side is implemented.

Rationale: a single source of truth for data and secrets keeps the web app thin and safe.

### II. Backend 3-Layer Architecture

- Every endpoint follows `routes → controllers → services → repositories` in `hoczi-api/src`.
- Controllers parse/validate input (DTOs in `src/dto` with `class-validator`) and map results to
  HTTP responses; they MUST NOT contain business logic or touch repositories.
- Services hold business rules and orchestration; they MUST NOT know about `req`/`res`.
- Repositories are the only layer that queries TypeORM/PostgreSQL.
- Errors MUST be thrown as `ApiError` subclasses (`src/errors/api-erros.ts`) and rendered by the
  error middleware; auth/roles via `authMiddleware` and `requireRole`.

Rationale: matches `hoczi-api/SKILL.md`; keeps logic testable and layers replaceable.

### III. Data & Migration Discipline

- Backend `synchronize` stays `false`. Every schema change MUST ship as a TypeORM migration in
  `hoczi-api/src/migrations` (`yarn migration:generate` / `migration:create`) and be reversible
  (`down` implemented).
- Entities live in `hoczi-api/src/entities`; multi-tenant data MUST be scoped by tenant/owner
  in the service layer.
- Destructive data changes (drop column/table, bulk delete) MUST be called out in the plan.

Rationale: production data is shared by schools/tenants; drift or silent loss is unacceptable.

### IV. AI & Knowledge Base Safety

- AI provider keys and config are server-only (`hoczi-api/src/config/ai.ts`); they MUST NOT be
  exposed through `NEXT_PUBLIC_*` variables or shipped to the browser.
- Learning content generated by AI (readings, grammar, exercises, answers) MUST be grounded in
  the Knowledge Base / RAG sources (e.g. HSK curriculum documents) when such sources exist, and
  MUST go through a draft/review state (`AiDraft`) before being published to learners.
- Every AI call MUST record usage (`AiUsageLog`) and handle timeouts/retries via `aiConfig`;
  long-running ingestion/generation runs in the worker (`src/worker.ts`), not in the request.
- Uploaded documents are untrusted input: validate type/size, never execute content.

Rationale: learners rely on correctness; cost and data leakage must stay controlled.

### V. Frontend Conventions (Next.js 16)

- `hoczi-web` uses Next.js 16 / React 19, which has breaking changes vs. older Next.js. Before
  writing routing, data-fetching or config code, read the relevant guide in
  `hoczi-web/node_modules/next/dist/docs/` (see `hoczi-web/AGENTS.md`).
- Route folders keep the pattern `page.tsx` (thin route entry) + `XxxPage.tsx` (component).
- API calls go through `data/services/*.service.ts`; shared types in `data/types.d.ts`.
- User-facing strings MUST be added to both `messages/vi.json` and `messages/en.json`
  (Vietnamese is the primary language).
- Styling uses Tailwind CSS 4 (+ SCSS where already used); icons from `lucide-react`.
- Admin features live under `app/admin/*` and MUST be reachable from the admin sidebar.

Rationale: consistency across many similar admin/learner pages; avoids stale-framework bugs.

### VI. Verification Gates

- A change is done only when, for every touched app:
  - `npx tsc --noEmit` passes (both apps);
  - `npm run lint` passes in `hoczi-web`;
  - `yarn build` (api) / `npm run build` (web) succeeds;
  - each user story's acceptance scenarios are verified manually (or by automated tests).
- No automated test framework exists yet. New non-trivial business logic in services SHOULD
  come with tests once a framework is introduced; introducing one is a plan-level decision.
- Results MUST be reported honestly — failing or skipped checks are stated, not hidden.

Rationale: explicit, achievable gates today, with a path to automated tests.

### VII. Spec-Driven & Simple

- Any non-trivial feature (new page, endpoint, entity, AI flow) MUST go through Spec Kit:
  `/speckit-specify` → (`/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`. Small fixes and copy changes may skip it.
- Specs describe WHAT/WHY for users (teachers, students, admins); plans describe HOW.
  Specs may be written in Vietnamese.
- Prefer extending existing modules over new abstractions (YAGNI). Any new dependency, service,
  or architectural layer MUST be justified in the plan's Complexity Tracking table.

Rationale: keeps intent reviewable and prevents scope creep in a small team.

## Technology & Security Constraints

- Backend: Node.js + TypeScript, Express 4, TypeORM 0.3, PostgreSQL, Redis (ioredis),
  Kafka (kafkajs), AWS S3/SES, OpenAI + Anthropic SDKs, PM2 (`ecosystem.config.js`), Docker.
- Frontend: Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, TipTap, axios.
- Secrets live only in `.env*` files (git-ignored) and deployment env; `env.example` MUST be
  updated whenever a new variable is introduced.
- Authentication via JWT/cookies; role checks enforced server-side, never only in the UI.

## Development Workflow

- Branch from `main`; feature branches created by `/speckit-specify` use sequential numbering
  (`specs/NNN-feature-name/`).
- Each feature folder holds `spec.md`, `plan.md`, `tasks.md` (and optional `research.md`,
  `data-model.md`, `contracts/`, `quickstart.md`).
- `/speckit-analyze` SHOULD be run before `/speckit-implement` on multi-story features.
- Commits are small and scoped; PRs reference the feature spec and state which Verification
  Gates were run.

## Governance

- This constitution supersedes ad-hoc instructions (e.g. `vibe_instruction.md`) where they
  conflict. Runtime agent guidance lives in `CLAUDE.md` (root) and `hoczi-web/AGENTS.md`.
- Every plan MUST pass the Constitution Check; violations are allowed only when justified in
  Complexity Tracking.
- Amendments are made via `/speckit-constitution`, versioned with semantic versioning
  (MAJOR: principle removed/redefined; MINOR: principle/section added or expanded;
  PATCH: wording), and recorded with an updated Last Amended date.
